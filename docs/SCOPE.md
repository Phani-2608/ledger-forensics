# Scope and limits

Read this before believing any number in this repository.

## What is measured

Every result is produced on documents this system generated. That is **internal
validity**: within the simulated world, the ground truth is exact, the masks are
pixel accurate, and the comparisons are fair.

## What is not measured

**Transfer to real receipts is unmeasured** unless you run the external validity
harness with your own images (`ledger_forensics/experiments/external.py`). A
detector that works on our renderer has not been shown to work on a photograph
of a real till roll. The unseen-generator experiment (E5) tests one part of this
by holding out an entire rendering configuration, but generator D is still our
code.

## The simulated OCR

The default reader returns the values actually rendered on the current image,
then injects character errors at a controlled rate that scales with image
quality.

- **What it costs**: no claim about real OCR accuracy follows from anything here.
- **What it buys**: OCR error rate becomes a dial. The attribution study needs
  to separate "the reader misread it" from "the detector missed it", and
  sweeping error from 0 to 2 percent while holding everything else fixed answers
  that far more cleanly than a fixed real engine would.

`TesseractOCR` in `extraction/ocr.py` is the drop-in swap point.

## The closed world

Tax rates, merchant templates, product catalogues and the transaction ledger are
defined in `world/registry.py` and generated by this system. Inside the
simulation they are ground truth, which is what makes the semantic checks
defensible. They assert nothing about real merchants or real tax law.

This is why checks like "tax rate matches the jurisdiction" are legitimate here
and would be fabricated knowledge in a system without a registry it controls.

## PRNU is deliberately absent

Camera sensor fingerprinting requires many images from one known physical device
to build a reference pattern. On synthetically rendered documents there is no
such device, so PRNU is not merely hard to validate, it is inapplicable.
Including it would have been the least defensible thing in the repository.

## Leave-one-attack-out is narrower than it looks

Only the fusion layer is learned. The six forensic detectors and nine semantic
checks are deterministic algorithms with no fitted parameters, so holding out an
attack class does not hide it from them. E4 tests whether the learned combiner
generalises to an evidence pattern it never saw during fitting. That is a real
question, but it is not "can the system detect an unseen attack", and the
results table says so.

## Prevalence is an assumption

The dataset is built balanced so the models have something to learn from. The
cost analysis resamples the test set to a low fraud rate before drawing any
conclusion about operating points, because at a 50 percent base rate reviewing
every case is trivially optimal and the threshold analysis would be
meaningless. The prevalence used is recorded in `results.json`.

## The cost model is stated, not derived

Review cost, recovery rate and false-accusation cost are parameters in
`decision/policy.py`. They are plausible, not measured. Change them and the
optimal operating point moves. That is the point of having them explicit.
